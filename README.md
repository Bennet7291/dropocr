# dropocr

拖拽图片到 exe 上，自动 OCR 识别中英文文字，在同目录生成
`yyyymmdd-hhmmss.txt`。单文件可执行程序，无 GUI/TUI/CLI，运行期
不产生除结果 txt 外的任何文件。

## 使用方法

把 `webp`/`jpeg`/`jpg`/`png` 图片拖拽到 `dropocr.exe` 上（支持
同时拖拽多个文件），每张图会各自生成一个带时间戳的 txt 文件。

## 编译前必读：这份工程目前缺一样东西

**`assets/` 目录下的三个文件（`det.onnx`、`rec.onnx`、`rec_dict.txt`）
需要你自己获取，本仓库不包含它们。** 具体步骤见 [MODELS.md](./MODELS.md)。

这不是疏忽——开发这份工程所在的沙盒环境完全没有网络路径能拿到
PaddleOCR 官方模型（托管服务不在可访问的域名范围内），也没法安装
PaddlePaddle 框架来做格式转换。这部分工作只能由你在自己的机器上
完成一次，之后就是普通的 `cargo build --release` 了。

## 编译方法

```bash
rustup target add x86_64-pc-windows-msvc
cargo build --release --target x86_64-pc-windows-msvc
```

产物在 `target/x86_64-pc-windows-msvc/release/dropocr.exe`。

如果你在 Windows 上直接编译（而不是交叉编译），去掉 `--target`
参数即可。

## 用 GitHub Actions 自动编译

`.github/workflows/build-windows.yml` 会在 `windows-latest` 上原生
编译（不做 Linux 交叉编译，省去 MSVC 链接器那一堆麻烦），打包成
`dropocr-windows-x64.zip`。

**用之前要先把 `assets/det.onnx`、`assets/rec.onnx`、`assets/rec_dict.txt`
提交到仓库**（或者配置成 Git LFS，workflow 已经开了 `lfs: true`）——
CI 没有办法替你生成这三个文件，原因见上面那节。没提交的话，workflow
会在编译前就直接报错退出，报错信息会明确指出缺哪个文件，不会让你去看
一堆不相关的 Rust 编译错误。

触发方式：
- 去 Actions 页面手动点 "Run workflow"，随时拿一个最新构建来测试
- `git tag v0.1.0 && git push origin v0.1.0`，除了照常构建，还会
  自动创建一个 GitHub Release 并把 zip 挂上去

这个 workflow 除了编译，还会做两件之前一直没条件做的事：

1. **跑一遍全部单元测试**（`cargo test --release --locked`）
2. **冒烟测试真实编译出的 exe**：先无参数运行一次（顺带验证
   `GetTimeZoneInformation` 这个 Win32 FFI 调用在真实 Windows 上不会
   崩溃——这是本工程唯一一处没在真机上跑过的 FFI 代码），再用
   PowerShell 现造一张带文字的图片真的拖给 exe 处理一次，确认
   **你的真实 PaddleOCR 模型**能被 tract 正常加载、完整识别流程能跑完
   不出错（不检查识别准确率，只确认整条链路在真机 + 真模型上不会
   当场崩溃——这一点在本工程开发过程中因为沙盒环境限制，一直只用
   我手写的极简 dummy 模型验证过，从没有机会验证过真实模型）。

如果这个冒烟测试失败，大概率说明真实模型的算子 tract 不完全支持，
或者模型输出的张量维度和 `detection.rs`/`recognition.rs` 里假设的不一致，
需要回头看 README「没有验证过的部分」那节。

**建议用最新 stable Rust**（本工程写作时对应 1.90+ 系列）。工程本身
不设置 `rust-version` 硬性下限，但仓库自带的 `Cargo.lock` 里锁定了
一些间接依赖的精确版本——这些版本号是在一个只有 Rust 1.75 的受限
沙盒环境里，为了验证代码正确性而手工降级摸索出来的，在你自己用
新版工具链编译时，其实不需要这么老的版本，可以放心 `cargo update`
升级到最新版本，通常不会有问题。保留 `Cargo.lock` 只是为了让首次
编译更快、更可预测。

## 这份工程做过哪些验证，哪些还没有

工程是在一个只有 Rust 1.75、且网络白名单很窄（拿不到 rustup 官方
安装脚本、拿不到 PaddleOCR 模型）的沙盒环境里开发的。这意味着**没法
在开发环境里对着真实 PaddleOCR 模型跑一次完整编译**。为了在这个限制
下尽量确保代码质量，做了以下几层验证，如实列出，方便你判断哪些地方
还需要你自己重点复核：

### 交付后又做过一轮自查，发现并修复了这些问题

代码写完交付后，又逐文件重新读了一遍，主动找问题而不是简单过一遍。
发现并修复了 5 个真实问题（不是吹毛求疵式的风格调整）：

1. **`main.rs` 用 `env::args()` 而不是 `env::args_os()`**——查了 Rust
   官方文档确认：`env::args()` 遇到非法 Unicode 的命令行参数会直接
   `panic`，整个进程崩溃退出、一个文件都处理不了。对一个靠拖拽任意
   文件路径驱动的工具来说，这是真实风险（哪怕概率不高）。已改成
   `args_os()`（永不因编码问题 panic）+ `Path::new()`，并用中文文件名
   实测过没问题。
2. **`detection.rs` 里 `index_axis` 存在越界 panic 的可能**——如果真实
   模型输出的张量在批次或通道维度上是空的（极端情况），会直接 panic
   而不是走已有的错误处理路径。加了一层形状检查，异常情况下返回
   `Err` 而不是让进程崩溃。
3. **`output.rs` 的 Win32 时区计算漏了 `StandardBias`**——写 FFI
   结构体那部分时，字段顺序/偏移量已经对照微软官方文档核实过是对的，
   但公式上只在夏令时叠加了 `DaylightBias`，没有在标准时间叠加
   `StandardBias`。查证微软文档后确认：标准时间下"真正的偏移"应该是
   `Bias + StandardBias`，不是只用 `Bias`。多数地区这个字段是 0，
   所以实际影响很小，但公式本身写得不完整，已按文档修正。
4. **检测区域数量没有上限**——如果某张图片被误检出成百上千个"文字
   区域"（复杂纹理照片、噪点较多的扫描件），识别阶段会把所有区域打包
   成一个巨大的 batch，可能导致内存占用剧增、耗时从秒级变成分钟级。
   这个工具没有进度提示，用户只会看到程序"卡住"。加了一个上限
   （默认 1000，按面积保留最大的区域），正常文档/截图远达不到这个
   数字，不影响正常使用。
5. **`OcrError::ImageDecode` 是个从未被用到的死分支**——图片解码在
   `main.rs` 里独立完成，从不经过 `OcrEngine`，这个分支保留在那里容易
   让人误以为解码错误会从 `OcrEngine` 内部抛出。已删除。

顺带清理了一处多余依赖（`Cargo.toml` 里显式声明的 `tract-core`
从未被直接引用，`tract-onnx` 已经通过 `prelude` 转发了需要的一切）。

修完这些之后，把完整工程重新在沙盒里编译 + 跑了一遍全部单元测试
（22 个，含新增的区域数量上限测试、两个世纪闰年边界测试用 Python
`datetime` 独立算出的天数交叉验证过），以及中文文件名的端到端拖拽
模拟测试，确认没有引入新问题、release 体积仍是 7.8MB（没有因为这些
修复增加体积负担）。

### 已经验证过、比较有把握的部分

- **核心推理链路可行性**：手写了两个结构极简但真实合法的 ONNX 模型
  （一个模拟 DBNet 输出结构，一个模拟 SVTR/CRNN 输出结构），验证了
  "用 `include_bytes!` 把模型嵌入二进制 → 从内存字节而非磁盘路径
  加载 → 设置动态维度 → tract 推理 → 解析输出"这条完整链路能跑通，
  且识别模型的推理数值结果和 `onnxruntime`（业界标准实现）在 1e-4
  精度内完全一致。
- **完整 pipeline 端到端跑通**：检测→区域提取→识别预处理→识别推理→
  有效步数换算→CTC解码，全链路用测试数据跑过，没有出现 panic、
  维度不匹配、类型错误。
- **CTC 解码逻辑**、**blank token 索引位置**（固定为 0）已对照
  PaddleOCR 官方 GitHub 源码 `rec_postprocess.py` 逐行核实一致。
- **DBNet 后处理的 unclip 膨胀公式**（`area/perimeter*ratio`）与
  官方实现一致；轮廓提取和外扩逻辑用手工构造的合理概率图验证过
  能正确提取矩形区域。
- **多文件拖拽、同秒文件名去重、不支持格式的容错处理、中文文件名**，
  都用真实编译出的二进制实测过，行为符合预期。
- **本地时间戳文件名**：没有引入任何日期时间第三方库，手写了
  Howard Hinnant 的日历换算算法（含两个专门针对"世纪闰年"这个最容易
  写错的 Gregorian 规则的边界测试，用 Python `datetime` 独立算出的
  天数交叉验证），时区偏移通过 FFI 直接调用 Win32
  `GetTimeZoneInformation`（系统自带 DLL，零依赖增量），字段布局和
  换算公式都对照过官方文档。
- **体积基线**：不含 OCR 模型本身的"骨架"部分（推理引擎+图像解码库
  编译后）实测约 7.8MB（Linux 构建），Windows 下数量级应该相近。

### 没有验证过、需要你重点关注的部分

- **Windows 环境本身**——所有验证都在 Linux 沙盒里做的（交叉编译
  Windows target 的实际产物没有跑过，因为沙盒没有 Windows 运行时）。
  `windows_subsystem = "windows"`（不弹控制台窗口）、拖拽传参、
  `GetTimeZoneInformation` FFI 调用，这几处 Windows 特有行为的
  最终验证需要你在真机上做。FFI 结构体字段布局和偏移量已经对照
  微软官方文档逐字段核实过，但终究没有在真实 Windows 上跑过。
  `.github/workflows/build-windows.yml` 已经把这一验证需求做进了
  CI（无参数冒烟测试会真实触发这个 FFI 调用），但这个 workflow
  本身也还没有被真正跑过一次——它经过的是我能做到的最大程度的
  静态核实（YAML 语法解析、PowerShell 语法逐行确认、专门实测过
  `panic=abort` 不会破坏 `cargo test` 的行为），不等于"已在真实
  Windows 上跑通"，你提交模型文件、推一个 tag 触发它一次，才算是
  真正验证完成。
- **真实 PaddleOCR 模型的实际加载与识别效果**——同上，CI 里的冒烟
  测试会用你提交的真实模型跑一次完整链路（不检查识别准确率，只
  确认不崩溃、不报错），但同样需要你实际跑一次 CI 才知道结果。
  检测模型真实输出的张量维度顺序（是否确实是 `[batch,channel,H,W]`）
  也没有用真实模型验证过，如果加载/推理阶段报 `UnexpectedOutputShape`，
  从这里开始排查。
- **最终体积能否真的压到 20MB**——骨架 7.8MB + 模型预算约 12MB
  的推算是合理的，但没有真实模型可用来实测验证。
- **AVIF / JXL 格式**——按之前约定完全没有实现，目前只支持
  webp/jpeg/jpg/png。
- **两个"低概率极端情况，已知但没有修复"的点**：(1) 如果同一秒内
  有两个完全独立的 exe 进程同时写同一个文件名（比如极端巧合下
  几乎同时启动了两次拖拽），存在小概率互相覆盖的竞态——没有修复，
  因为解决它需要在文件名里加额外的随机/PID 信息，会破坏你要求的
  `yyyymmdd-hhmmss.txt` 精确格式；(2) 字典文件里如果出现重复 token，
  `OcrEngine::new()` 会直接返回错误（整个工具在这次运行里都无法
  处理任何文件）——这是特意设计成"宁可启动失败"而不是"静默接受可能
  损坏的字典"，因为字典错位这类问题一旦被默默接受，会让所有识别
  结果都不知不觉地错，比启动失败更难发现。用官方原始字典文件不会
  触发这个检查。

### 一处主动做的技术取舍，供你判断是否需要调整

DBNet 检测框的 unclip 膨胀，本工程用的是**外接矩形外扩**而非精确的
Vatti clipping 多边形偏移。原因：`i_overlay` 这类多边形偏移库的
具体 API 在不同版本间变动较大，在受限沙盒里没能验证清楚，为了保证
"编译一定能过"优先于"轮廓精度的最后一点提升"，选择了更简单可靠的
矩形外扩方案。对绝大多数横排文字场景（截图、文档、网页截屏）精度
损失很小；如果你的场景里有大量明显倾斜的文字（比如拍照的招牌），
这里的精度可能不够，可以在 `src/ocr/postprocessing.rs` 的
`unclip_polygon` 函数里替换成真正的多边形偏移实现。

## 项目结构

```
src/
├── main.rs              程序入口：参数处理、文件遍历、输出写入
├── output.rs             时间戳生成、结果格式化
└── ocr/
    ├── mod.rs             OCR 引擎入口，串联检测+识别
    ├── detection.rs       DBNet 检测模型推理（从内存加载）
    ├── recognition.rs     SVTR/CRNN 识别模型推理（从内存加载）
    ├── preprocessing.rs   图像预处理（检测+识别两套）
    ├── postprocessing.rs  检测后处理（轮廓提取、unclip外扩）
    ├── ctc.rs              CTC 贪心解码
    └── dictionary.rs       识别字典加载
assets/                    模型和字典文件（需要你自己放进去，见 MODELS.md）
MODELS.md                  模型获取/转换详细步骤
```
